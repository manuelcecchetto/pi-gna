# iOS Safari / Home Screen constraints for the pi-gna mobile client

Status: research note for the iPhone remote epic (`docs/plans/draft/iphone-remote.md`; `docs/REMOTE.md` is the contract
and wins on conflict). Researched 2026-10-04. Each constraint has a source, the design consequence for pi-gna, and a
confidence tag:

- **[sourced]**: read in the linked primary source during this research.
- **[known]**: long-standing documented platform behavior, linked, but not re-read here; confirm on a device if a design depends on the detail.
- **[device]**: cannot be settled from documents; goes into the real-device list at the end (input for T21's runbook).

The Xcode iOS Simulator is **not installed** on the research machine (`xcrun simctl` fails: "not a developer tool"), so
nothing here was observed in a simulator. Standalone mode needs a manual Add to Home Screen anyway, even on a simulator.

## 1. Storage and sessions

| # | Constraint | Source | Design consequence |
|---|---|---|---|
| 1 | A Home Screen web app has **its own storage, isolated from Safari** (cookies, localStorage, IndexedDB, SW). Apple closed the report "by design". Present at least since iOS 11.3. **[sourced]** | [WebKit bug 181849](https://bugs.webkit.org/show_bug.cgi?id=181849) (Brent Fulgham: "created as isolated entities without shared state with the browser") | **Pairing must happen inside the installed app**, never in a Safari tab beforehand. The first-run page in Safari only explains "Add to Home Screen, open it, pair there". A token/cookie obtained in Safari is invisible to the app. A Safari tab and the installed app are two separate devices for the server (each needs its own pairing, each shows up separately in the paired-devices list). |
| 2 | Multiple installs of one web app are allowed; the app identity is the manifest `id` plus the user-chosen name (iOS 16.4+). **[sourced]** | [WebKit: Web Push for Web Apps](https://webkit.org/blog/13878/web-push-for-web-apps-on-ios-and-ipados/) | Set a stable manifest `id` (e.g. `/`) so identity does not drift between releases. Treat every install as its own device record. |
| 3 | iOS 17.2 to 17.5.x (reports up to 18.1): **session cookies** (no `Max-Age`/`Expires`) in Home Screen apps are intermittently reverted to older values (or dropped) after the app is closed/reopened; `document.cookie` still shows the new value while the `Cookie` header carries the old one. Reproduced by Apple on 17.5/17.5.1, not on iOS 18 beta 2; never declared fixed; later reports on 18.1. Cookies set as persistent (explicit `Max-Age`) did not reproduce in the reporter's tests. **[sourced]** | [WebKit bug 272325](https://bugs.webkit.org/show_bug.cgi?id=272325) | The auth cookie is **persistent** (`Max-Age` of weeks/months, `Secure`, `HttpOnly`, `SameSite=Strict`), never a session cookie. Do not rely on a *pair* of cookies that change together: use one opaque device token cookie that never rotates silently. If rotation is ever needed, accept the previous value for a short grace window (server side), because a stale value may arrive. Keep the server's 401 path graceful: the client shows "re-pair" only after a stale-cookie retry fails once. |
| 4 | ITP caps script-writable storage (IndexedDB, localStorage, SessionStorage, SW registrations and caches) at **7 days of Safari use without interaction on the site** and deletes it. Home Screen apps have **their own usage counter** reset by real use; Apple says deletion there would be "a serious bug". HttpOnly server-set cookies are not script-writable and are not covered by that cap. **[sourced]** | [WebKit: Full Third-Party Cookie Blocking and More](https://webkit.org/blog/10218/full-third-party-cookie-blocking-and-more/), section "A Note On Web Applications Added to the Home Screen" | Installed app: fine. **A Safari tab can lose localStorage after a week of not visiting.** So nothing precious lives only in client storage: the host holds pins, bookmarks, ATP threads, settings (already the plan: move them to main). Client storage is a cache of UI prefs and a pairing hint only. Server-set `HttpOnly` cookie carries the credential, not localStorage. |
| 5 | iOS can evict a web app's storage under device storage pressure. **[known]** | [Apple: Updates to Storage Policy](https://webkit.org/blog/14403/updates-to-storage-policy/) | Same as 4: the host is the source of truth; losing client storage costs a re-pair at worst, never data. |

## 2. Network: EventSource, fetch, suspension

| # | Constraint | Source | Design consequence |
|---|---|---|---|
| 6 | When the app goes to the background/locks, iOS suspends the page; the network connection (SSE/EventSource, fetch streams, WebSocket) is dropped or silently dead, and timers stop. On resume the page may have an `EventSource` in `readyState` OPEN that no longer receives data, or a CLOSED one. **[known]; exact timings [device]** | [MDN: EventSource](https://developer.mozilla.org/en-US/docs/Web/API/EventSource), [MDN: Page Visibility](https://developer.mozilla.org/en-US/docs/Web/API/Page_Visibility_API); WebKit has no document for suspension timings | The client must not trust the connection state. **Reconnect triggers:** `visibilitychange` to visible, `pageshow` (including `persisted`), `online`, `focus`, and `freeze`/`resume` where available. On any of them, assume the stream is dead: close and re-open with the last seen sequence number (`Last-Event-ID` or explicit param) and let the server replay from its ring buffer or send a snapshot when the gap is too big. Add a **heartbeat watchdog** (server sends a comment/event every ~15 s; client reconnects if nothing arrives for ~2.5 intervals) to catch the "OPEN but dead" case. |
| 7 | `EventSource` auto-reconnects only on network errors; on an HTTP error status (401, 5xx behind Tailscale/serve) it gives up (CLOSED) and does **not** retry. It also cannot set custom headers. **[known]** | [WHATWG HTML: server-sent events](https://html.spec.whatwg.org/multipage/server-sent-events.html#processing-model), [MDN: EventSource](https://developer.mozilla.org/en-US/docs/Web/API/EventSource) | Auth by cookie (works with EventSource, same origin), not headers. Own the retry loop: on `error` with CLOSED, retry with capped exponential backoff and re-check `/session`-style auth endpoint to distinguish "host asleep/offline" (retry, show banner) from "revoked" (go to pairing). Prefer `fetch` streaming or a small reader only if tests show EventSource is unreliable; design the event channel so the transport is swappable. |
| 8 | HTTP/1.1 connection limits per host in Safari are 6; EventSource uses one. Over `tailscale serve` (HTTPS, HTTP/2 to the browser) this is not a practical problem. **[known]** | [MDN: EventSource](https://developer.mozilla.org/en-US/docs/Web/API/EventSource) (connection-limit note) | One SSE stream per client (multiplexing chats), not one per chat. |
| 9 | Nothing keeps working in the background: no background fetch/sync, no long-lived streams. Wake Lock (`navigator.wakeLock`) works on iOS 16.4+ and only keeps the screen on while the page is visible. **[sourced for Wake Lock availability]** | [WebKit: Web Push for Web Apps](https://webkit.org/blog/13878/web-push-for-web-apps-on-ios-and-ipados/) (lists Screen Wake Lock API) | Host work must never depend on the phone staying connected (already a plan constraint). Optional "keep screen on while a run is active" toggle; not required for correctness. Completion/approval alerts while backgrounded are only possible through Web Push (row 17). |
| 10 | Mixed content/`ws://` to a `http` origin is blocked; the app is only served over HTTPS (`tailscale serve`). A Tailscale HTTPS cert is public-CT-logged hostname metadata but traffic stays on the tailnet. **[known]** | [MDN: Mixed content](https://developer.mozilla.org/en-US/docs/Web/Security/Mixed_content), [Tailscale: serve](https://tailscale.com/kb/1242/tailscale-serve) | No plain HTTP fallback is offered. The install flow documents that the iPhone needs the Tailscale app connected (VPN on) for the page to load at all. |

## 3. Service worker and manifest

| # | Constraint | Source | Design consequence |
|---|---|---|---|
| 11 | Service workers are supported in standalone web apps and Safari (iOS 11.3+), require a secure context, and scope is limited to the SW script's path (served at `/sw.js` for scope `/`). **[known]** | [MDN: Service Worker API](https://developer.mozilla.org/en-US/docs/Web/API/Service_Worker_API), [MDN: ServiceWorkerContainer.register scope](https://developer.mozilla.org/en-US/docs/Web/API/ServiceWorkerContainer/register) | Serve `sw.js` from the root with `Service-Worker-Allowed` not needed. **The SW caches only the static shell (hashed build assets + index), never `/api`, the event stream, uploads or any authenticated JSON.** Navigation requests are network-first with a cached-shell fallback so an offline/host-asleep phone shows the app chrome plus a "host unreachable" state rather than a browser error page. |
| 12 | iOS checks for a new SW on navigation and at most about once per 24 h otherwise; an updated worker waits until all clients close unless it calls `skipWaiting()`. A standalone app is rarely fully closed. Update timing is a known source of "stuck on old version" reports. **[known]; behavior [device]** | [MDN: Using Service Workers, updates](https://developer.mozilla.org/en-US/docs/Web/API/Service_Worker_API/Using_Service_Workers#updating_your_service_worker), [web.dev: service worker lifecycle](https://web.dev/articles/service-worker-lifecycle) | Version the shell: the server exposes a build id (header/`/version`); the client compares on every resume (row 6 trigger) and, if different, calls `registration.update()` then shows an "Update ready, reload" prompt (or reloads when idle). Serve `sw.js` and `index.html` with `Cache-Control: no-cache`. Hashed assets `immutable`. Keep the protocol version in the handshake so an old cached client against a newer host gets a clear "update" message instead of silent breakage. |
| 13 | Manifest: iOS honors `display: standalone`/`fullscreen` (this is what makes it a web app), `name`/`short_name`, `id`, `start_url`, `scope`, and manifest `icons`. `apple-touch-icon` link takes precedence over manifest icons. Without icons iOS makes a monogram (16.4+). `theme_color`/`background_color` are partly ignored; the status-bar look is controlled by `<meta name="apple-mobile-web-app-status-bar-style">` (`default`, `black`, `black-translucent`) and `<meta name="theme-color">` in newer iOS. The splash screen is not generated from the manifest (needs `apple-touch-startup-image` per device size or it shows a blank/background colour). **[sourced for display, id, icons, precedence]; status bar/splash [known]** | [WebKit: Web Push for Web Apps](https://webkit.org/blog/13878/web-push-for-web-apps-on-ios-and-ipados/), [MDN: Web app manifest](https://developer.mozilla.org/en-US/docs/Web/Manifest), [Apple: Configuring web applications](https://developer.apple.com/library/archive/documentation/AppleApplications/Reference/SafariWebContent/ConfiguringWebApplications/ConfiguringWebApplications.html) | Ship: manifest with `display: standalone`, `id`, `start_url`, `scope`, 180x180 `apple-touch-icon` (opaque, no transparency; iOS fills transparent areas with black), 192/512 manifest icons; `apple-mobile-web-app-capable` meta for old iOS; `black-translucent` only if the layout handles the safe area (row 14), else `default`. Skip splash images at first (set `background_color` to the app background so the blank frame matches). |
| 14 | In standalone mode there is **no browser chrome**: no back button, no reload, no URL bar; navigation outside `scope` opens an in-app Safari sheet; the edge-swipe back gesture exists but only for history entries. **[known]** | [Apple: Configuring web applications](https://developer.apple.com/library/archive/documentation/AppleApplications/Reference/SafariWebContent/ConfiguringWebApplications/ConfiguringWebApplications.html) | Every screen needs an in-app back/close affordance and a visible "reload/reconnect" action (pull-to-refresh is not provided). Use `history.pushState` for chat/detail screens so the edge swipe works. OAuth/`openExternal` links leave scope on purpose; open them via `<a target=_blank>` and expect to return by switching apps. |

## 4. Layout, keyboard, input

| # | Constraint | Source | Design consequence |
|---|---|---|---|
| 15 | `viewport-fit=cover` plus `env(safe-area-inset-*)` is needed to draw edge to edge and avoid the notch/home indicator; in standalone with `black-translucent` the content goes under the status bar. **[known]** | [WebKit: Designing Websites for iPhone X](https://webkit.org/blog/7929/designing-websites-for-iphone-x/), [MDN: env()](https://developer.mozilla.org/en-US/docs/Web/CSS/env) | `<meta name="viewport" content="width=device-width, initial-scale=1, viewport-fit=cover">`; pad header/composer with `env(safe-area-inset-top/bottom)`. **Device findings (iOS 26/27, 2026-10):** with `black-translucent`, `height: 100%`/`dvh` started out short by the top inset (59 px), leaving a gap under the composer; with `default` (below) `100vh` is taller than the page and the whole page scrolls. So on iOS `viewport.ts` sets `--app-height` to `visualViewport.height` (row 16) and the root uses it. iOS blurs the top of a standalone app (Liquid Glass scroll edge effect). WebKit hides it only through a fixed color extension: `Page::updateFixedContainerEdges` hit-tests 4 px inside the fixed layout rect for a fixed/sticky box over 10 px with a solid background (`LocalFrameView::fixedContainerEdges`), and `-[WKWebView _updateFixedColorExtensionViews]` skips a side whose obscured inset is 0. With `black-translucent` the page runs under the status bar, so the top inset is most likely 0 and nothing removes the blur: a fixed band, a sticky header and a sticky header padded into the inset all failed on the device (2026-10-05). So the meta is `default` and the sticky solid `Header` is the sampled element (a 12 px fixed band painted over the header clipped two-line titles; it now sits under the app shell and only serves header-less screens). Keep a fixed or sticky top element for the page's whole life (sampling runs only on load commit, fixed elements added/removed, and inset changes, and the top edge only until the user interacts). The status-bar meta is read at install: changing it needs delete, re-add and re-pair. Sources: [piclaw PWA notes](https://github.com/rcarmo/piclaw/blob/HEAD/docs/PWA.md), [ojapp write-up](https://tips.ojapp.app/en/ios-27-pwa-top-blur-workaround-2/), WebKit `WKWebView.mm`, `Page.cpp`, `LocalFrameView.cpp`. |
| 16 | **Keyboard**: on iOS the on-screen keyboard does **not** resize the layout viewport (nor the initial containing block, nor `100vh`/`100dvh`); it overlays and Safari scrolls the page. `window.visualViewport` (iOS 13+) reports the visible area (`height`, `offsetTop`) and fires `resize`/`scroll`. The interactive-widget meta (`resizes-content`) is not supported on Safari. Inputs with computed font-size below 16 px trigger an automatic **zoom-on-focus**. **[known]; exact numbers [device]** | [MDN: VisualViewport](https://developer.mozilla.org/en-US/docs/Web/API/VisualViewport), [MDN: `interactive-widget`](https://developer.mozilla.org/en-US/docs/Web/HTML/Viewport_meta_tag#interactive-widget) | The composer docks to the **visual** viewport: a small hook reads `visualViewport.height/offsetTop` and sets a CSS var (`--vvh`, `--vv-offset`) on `resize`/`scroll`; the chat layout uses it instead of `100vh`. Composer text is `font-size: 16px` minimum. Do not use `position: fixed` bottom bars without the hook (they jump when the keyboard opens). Scroll-to-bottom on focus is handled in app code. **Built (2026-10):** `src/mobile/viewport.ts` sets `--app-height` from `visualViewport.height`, toggles `html.keyboard` (drops the bottom safe-area padding; detected against the tallest visible height per width, since iOS shrinks `window.innerHeight` with the keyboard too, which left a 42 pt gap above it), and resets `scrollTo(0,0)` on viewport scroll and after focus changes, because iOS pans the page to reveal the field and took the header with it. It also sets `--device-radius` from the screen size (UIScreen's `_displayCornerRadius` values, kylebshr/ScreenCorners; the web cannot read it) for concentric sheets (`.concentric-sheet`), iOS only. The composer is a capsule (as iOS's own bottom controls are): a 44 px field can't follow a 62 pt display corner, and an attempt at concentric composer corners clipped its buttons (device check 2026-10-05). |
| 17 | File input: `<input type="file" accept="image/*">` opens the iOS sheet (Photo Library, Take Photo, Choose Files); `capture` forces the camera. Files app picks work; **HEIC** photos are usually converted to JPEG by Safari when `accept` is `image/*` but not guaranteed (when accept lists specific types the OS may transcode, when it lists none, HEIC may be delivered as is). Camera uploads can be large (several MB); EXIF orientation applies. **[known]; HEIC behavior [device]** | [MDN: `<input type=file>`](https://developer.mozilla.org/en-US/docs/Web/HTML/Element/input/file), [MDN: capture attribute](https://developer.mozilla.org/en-US/docs/Web/HTML/Attributes/capture) | Attachments are **uploads** (host cannot read phone paths; `webUtils.getPathForFile`/`pickAttachments` do not exist remotely). The server accepts any image MIME incl. `image/heic` and either converts on the host (`sips` is on macOS, no install) or rejects with a clear error; the client downscales large images (canvas) before upload as an optimization only. Enforce a size cap and stream the body. |
| 18 | Clipboard: `navigator.clipboard.writeText` works in secure contexts but **only inside a user gesture**; `readText` triggers an iOS "Paste" confirmation bubble each time; `ClipboardItem` image read/write is limited. `document.execCommand('copy')` fallback is needed for gestures that lose activation after `await`. **[known]; exact behavior [device]** | [MDN: Clipboard API](https://developer.mozilla.org/en-US/docs/Web/API/Clipboard_API), [WebKit: Clipboard API](https://webkit.org/blog/10855/async-clipboard-api/) | Copy buttons call `writeText` synchronously in the click handler (no `await` before it; resolve text first). Never read the clipboard programmatically: use normal paste into the composer. Pasting images from the clipboard into the composer goes through the `paste` event. |
| 19 | Text selection and context menus on long-press, tap highlight, rubber-band overscroll and double-tap zoom are default; `touch-action: manipulation` removes double-tap zoom delay. **[known]** | [MDN: touch-action](https://developer.mozilla.org/en-US/docs/Web/CSS/touch-action) | Set `touch-action: manipulation` on controls; `overscroll-behavior: none` on the app shell; allow selection in transcript text (users copy output). |

## 5. Push notifications

| # | Constraint | Source | Design consequence |
|---|---|---|---|
| 20 | Web Push on iOS/iPadOS needs **16.4+**, the site **added to the Home Screen** (not available in a Safari tab), a manifest with `display: standalone`/`fullscreen`, a service worker with a `push` handler, and the permission request **in direct response to a user gesture** (a "Enable notifications" button). iOS then shows its own prompt; the user can manage it per web app in Settings > Notifications, with Focus support. Pushes must show a notification (silent pushes are not allowed; repeated ones that do not are revoked). **[sourced]** | [WebKit: Web Push for Web Apps on iOS and iPadOS](https://webkit.org/blog/13878/web-push-for-web-apps-on-ios-and-ipados/), [WebKit: Meet Web Push](https://webkit.org/blog/12945/meet-web-push/) | Push is a **later, optional layer**: the base design works with in-app signals (title/badge while foreground, banner on resume). When built: an explicit button inside the installed app, a feature check (`'PushManager' in window` and `navigator.standalone`/`display-mode: standalone`) before offering it, always `userVisibleOnly: true`, notification payload carries only a short title and a chat id, **never message content or paths** (it transits Apple's push service). Push needs the host to reach Apple's/Web Push endpoints and VAPID keys generated and stored on the host; this is new outbound network use and has to be an explicit opt-in. |
| 21 | App badge (`navigator.setAppBadge`) works in Home Screen web apps 16.4+, set in foreground or in the push handler. **[sourced]** | [WebKit: Web Push for Web Apps](https://webkit.org/blog/13878/web-push-for-web-apps-on-ios-and-ipados/) | Optional: badge = number of chats awaiting approval/input. Not a dependency. |

## 6. Memory, processes, inline visuals

| # | Constraint | Source | Design consequence |
|---|---|---|---|
| 22 | iOS Safari/standalone web content processes have a hard memory ceiling (no published number; large pages and many iframes get the page killed and reloaded, showing "A problem repeatedly occurred" or a silent reload); background pages are discarded at will. `sandbox`ed `srcdoc` iframes are supported. **[known]; limits [device]** | [Apple: WKWebView memory/web content process (discussion)](https://developer.apple.com/forums/thread/749364), [MDN: iframe sandbox/srcdoc](https://developer.mozilla.org/en-US/docs/Web/HTML/Element/iframe) | The mobile client must survive a **page reload at any time** (a content-process kill looks like a fresh load): all state is re-derivable from host snapshot + event replay, scroll position and composer draft persist in `sessionStorage`/`localStorage` (cache, per row 4). Virtualize/trim long transcripts; render inline visuals (sandboxed `srcdoc` iframes) lazily when scrolled into view and unload offscreen ones; cap concurrent live visuals (start at a few) and pause scripts of offscreen ones by replacing `srcdoc`. Never put the full browser/remote screen stream in the same page as a long transcript without a budget. |
| 23 | In a Home Screen app, `window.open`/new tabs behave differently; cross-origin popups are not meaningful. **[known]** | [Apple: Configuring web applications](https://developer.apple.com/library/archive/documentation/AppleApplications/Reference/SafariWebContent/ConfiguringWebApplications/ConfiguringWebApplications.html) | Avoid popups. Links open as normal navigations (in-app sheet for out-of-scope). |

## 7. Observable without a device

- Simulator: **unavailable here** (no Xcode). If available later: `xcrun simctl boot <device>; xcrun simctl openurl booted https://...`
  loads the page in Mobile Safari (not standalone). Simulator Safari needs a trusted HTTPS cert for secure-context APIs
  (SW, clipboard, push); `localhost`/`127.0.0.1` count as secure, `*.ts.net` over the tailnet only works on a real device
  (the simulator shares the Mac's network, so a Tailscale-served URL also works from the Mac).
- Desktop Safari/WebKit with Responsive Design Mode can exercise layout, `visualViewport` hook logic (partly), manifest
  parsing and SW logic, but **not** iOS keyboard, standalone chrome, storage isolation, suspension or push.
- Chromium-based emulation (what `docs/RESPONSIVE_BROWSER.md` style checks use) is useful for layout only; do not treat it
  as evidence for any row above tagged [known] or [device].

## 8. Real-device checklist (feed for T21's runbook)

Run on an iPhone (note iOS version), once in a Safari tab and once from the Home Screen:

1. **Storage isolation (row 1):** pair in Safari, add to Home Screen, open it: must ask to pair again; both appear as separate devices in the host's list.
2. **Cookie persistence (rows 3, 4):** after pairing in the installed app, force-quit it, reboot the phone, wait a day, open it: still paired. Record iOS version. Repeat across 3 days without opening a Safari tab. Verify the cookie has `Max-Age`.
3. **Reconnect (rows 6, 7):** start a run, lock the phone 30 s / 5 min / 30 min, unlock: the transcript catches up with no duplicated or missing events; time-to-live and whether the stream was OPEN-but-dead. Toggle airplane mode and Tailscale off/on; turn the host Mac's server off then on (banner vs re-pair).
4. **Host asleep (row 9):** host lid closed or asleep: client shows "host unreachable", and recovers when the host wakes without a re-pair.
5. **SW update (row 12):** deploy a new build, open the installed app: how long until the new version shows, whether the update prompt appears, and that an old client against a new host gets the protocol message.
6. **Keyboard/safe area (rows 15, 16):** composer position with keyboard up in portrait/landscape, with the predictive bar, with `black-translucent`/`default`; no zoom on focus; scroll to the latest message stays correct.
7. **Uploads (row 17):** Take Photo, Photo Library (HEIC original), Files; a 10+ MB photo; check what MIME/extension arrives on the host.
8. **Clipboard (row 18):** copy buttons (code blocks, message) work first tap; paste an image into the composer.
9. **Memory (row 22):** a long transcript (thousands of lines) plus 5+ inline visuals plus a browser view; background for 10 min and return: reload happens or not, state restored.
10. **Push, if built (rows 20, 21):** button inside the installed app triggers the iOS prompt; works when the app is closed; absence of the option in a Safari tab.
11. **Standalone chrome (rows 13, 14):** status-bar style, icon, name, every screen has a way back, OAuth/external link return path.
